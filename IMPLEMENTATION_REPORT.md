## D3. Единая работа с данными (и закрытие R1–R7)

### R1. Веб использует выбранный набор данных

- `app.py` больше не берёт `menu_store.default_store_path`: все пути идут через
  `kitchen/web/dataset.Dataset.default()` (каталог `SHEGCHEF_DATA_DIR`, по
  умолчанию `~/.shegchef`). Обычный запуск Streamlit читает **оба** имени меню
  (`menu.json` и `меню.json`), а конфликт одной даты показывает ошибкой до
  записи. Явный файл меню для веба — `SHEGCHEF_MENU_FILE`; у CLI — `--menu-file`.
- Настройки/статусы/отклонения/отчёт берутся из тех же путей каталога.
- Проверки: `tests/test_app_dataset.py` — меню только в «меню.json»;
  непересекающиеся даты двух файлов; конфликт одной даты; снятие конфликта
  явным файлом; сохранение без потери других дат. Всё — через AppTest и
  конфигурацию запуска, без ручной подмены `session_state`/модульных атрибутов.

- `tests/test_cli_data_store.py::test_cli_absent_next_day_is_absence_not_book_plan`

### R4. Выходная книга сама меню не выбирает

  политика. Сохранённая пустая дата не заменяется строками книги.
- Добавлен ключ `--from-book`; сценарий ручной правки Excel сохранён и

### R6. JSON null и скаляры — ошибка, а не отсутствие файла

- Причина дефекта: `dataset._read_json` возвращал `None` и для отсутствующего
  файла, и для JSON `null`; `_load_one` трактовал `None` как «меню нет».
  Теперь отсутствие проверяется по самому файлу (`path.exists()`), а
  `_load_one` требует `Mapping`: существующий `null`, `false`, число, строка
  или список дают `DataStoreError`, при этом исходные байты не меняются.
- Остальные четыре хранилища (настройки, комментарии/отклонения, статусы,
  отчёты) уже поднимали свой `StoreError` на `null` и скаляры — их штатные
  загрузчики/сохранения покрыты регрессиями без искусственного Dataset API.
- Воспроизводящие регрессии в `tests/test_dataset.py`
  (`test_scalar_json_is_error_not_missing_file`, `..._in_alt_name_is_error`,
  `test_explicit_scalar_file_is_error`, `test_missing_file_still_is_empty`)
  и `tests/test_store_protection.py` (параметризованные `null`/`false`/число/
  строка для всех пяти хранилищ, включая отказ сохранять поверх и сохранность
  байтов). До исправления `null`-случаи падали.

### R7. Сохранение веб-правок соответствует выбранному источнику

- Причина дефекта: `app.persist_store` всегда писал в `dataset().menu`, тогда
  как чтение могло идти из `SHEGCHEF_MENU_FILE` или `меню.json`. Правка даты
  из `меню.json` создавала вторую запись в `menu.json` и конфликт.
- Добавлен `Dataset.menu_write_targets(day_key)`: явный `SHEGCHEF_MENU_FILE`
  — единственный адресат; иначе запись идёт в те существующие файлы
  (`menu.json`/`меню.json`), где дата уже есть; новые даты — в `menu.json`.
  `persist_store` сохраняет во все выбранные адреса, поэтому одинаковые копии
  даты в двух файлах остаются согласованными, а правка из `меню.json` больше
  не рождает конфликт. Второй файл без явного выбора не затрагивается.
- Воспроизводящие AppTest-регрессии в `tests/test_app_dataset.py`:
  `test_web_saves_to_explicit_menu_file_and_reopens` (override вне каталога,
  правка порций, смена даты, новая сессия, отсутствие постороннего `menu.json`),
  `test_web_edits_menu_from_alt_name_without_conflict` (дата только в
  `меню.json`, другие даты в `menu.json`, переоткрытие без конфликта),
  `test_web_refuses_to_save_while_menu_conflict` (запись запрещена, файлы целы)
  и `test_web_conflict_saves_the_chosen_file_only` (правка только выбранного
  файла, второй неизменен). Проверено, что до исправления они падают.
