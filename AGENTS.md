# Правила работы над ShegChef

Этот файл — постоянный контракт для всех AI-агентов и разработчиков проекта.
Требования конкретной задачи находятся в `TASK.md`. Если инструкции расходятся,
приоритет имеют явные указания пользователя, затем `TASK.md`, затем этот файл.

## Роли

- **Продакт (ChatGPT/Codex):** формулирует цель, границы задачи, приоритет и проверяемые
  критерии приёмки. Не диктует реализацию без продуктовой необходимости.
- **Разработчик (OpenCode + coding-модель):** реализует только согласованный scope,
  добавляет или обновляет тесты и заполняет `IMPLEMENTATION_REPORT.md`.
- **QA (Hermes + Laguna S 2.1 Free, либо другая coding-модель):** независимо проверяет требования из
  `TASK.md`, выполняет тесты и фиксирует результаты в `QA_REPORT.md`.
- **Приёмка (ChatGPT):** сверяет результат с целью и acceptance criteria, а не
  только с наличием зелёных тестов.

Разработчик не изменяет acceptance criteria самостоятельно. Неясность или
противоречие возвращается продакту как вопрос или явно записанное допущение.

## Контекст проекта

ShegChef — локальный планировщик кухонной смены на Python. Он рассчитывает
продукты, задачи и обратный тайминг, а затем выдаёт результат через Excel,
CLI или Streamlit.

- `kitchen/core/` — доменные расчёты; не должен зависеть от Excel и Streamlit.
- `kitchen/excel/` — чтение и сборка книги Excel.
- `kitchen/web/` — чистая логика веб-сценариев без Streamlit.
- `app.py` — UI Streamlit.
- `build.py` — CLI.
- `tests/` — автоматические тесты.
- `startconcept/` — исходные концепции и спецификации; не менять без явной задачи.

Поддерживается Python 3.10+. Зависимости перечислены в `requirements.txt`.

## Рабочий цикл

1. Продакт заполняет `TASK.md`: цель, scope, non-goals и acceptance criteria.
2. Разработчик изучает `TASK.md`, связанные модули и тесты до внесения изменений.
3. Разработчик делает минимальный связный diff, обновляет тесты и
   `IMPLEMENTATION_REPORT.md`.
4. QA проверяет каждый критерий, запускает регрессию и обновляет `QA_REPORT.md`.
5. При дефектах разработчик исправляет реализацию, после чего QA повторяет прогон.
6. Продакт принимает результат либо возвращает задачу с конкретными замечаниями.

## Правила реализации

- Сохранять разделение слоёв: доменная логика — в `kitchen/core/` или чистых
  модулях, отображение — в Excel/Streamlit-слое.
- Не добавлять сетевые сервисы, базы данных, авторизацию или отправку сообщений,
  если это не входит в задачу.
- Не менять публичное поведение CLI и форматы книги без явного критерия приёмки.
- Не подменять существующие пользовательские данные демо-данными.
- Для исправления дефекта сначала добавлять тест, который его воспроизводит,
  если это практически возможно.
- Не редактировать и не удалять несвязанные изменения в рабочем дереве.
- Новая зависимость требует обоснования в `IMPLEMENTATION_REPORT.md`.

## Проверки

Основная регрессия:

```bash
.venv/bin/python -m pytest tests/ -q
```

Точечный прогон:

```bash
.venv/bin/python -m pytest tests/test_<area>.py -q
```

Для изменений CLI дополнительно запускать затронутый сценарий с `--no-open` и
временным выходным файлом. Для Excel проверять не только создание файла, но и
значения, ссылки и структуру листов автоматическими тестами. Для Streamlit
предпочитать AppTest и тестирование чистой логики в `kitchen/web/`.

## Definition of Done

Задача завершена, когда:

- выполнены все acceptance criteria из `TASK.md`;
- добавлены или обновлены релевантные тесты;
- полная регрессия завершилась успешно либо известные сбои явно описаны;
- `IMPLEMENTATION_REPORT.md` отражает фактический diff и проверки;
- `QA_REPORT.md` содержит независимый вердикт и воспроизводимые результаты;
- не осталось необъяснённых изменений вне scope.
