# Проект: конструктор управления кухней

Нужно начать разработку первой рабочей версии системы управления кухней для шеф-повара.

## Контекст

Цель системы — дать шеф-повару возможность собрать меню из ТТК и автоматически получить рабочий план кухни:

* необходимое количество продуктов и заготовок;
* распределение обязанностей между сотрудниками;
* обратный тайминг от времени выдачи;
* контрольные точки;
* данные для дальнейших закупок, списаний и инвентаризации.

Основная идея:

**Шеф выбирает блюда + количество порций + время выдачи → система превращает это в план работы кухни на смену.**

В качестве основы первой версии используется **Excel-таблица**. Не нужно строить отдельную базу данных вроде PostgreSQL и не нужно превращать проект в сложное веб-приложение.

Таблица должна оставаться понятной человеку и пригодной для ручного редактирования.

## Главный сценарий MVP

Нужно реализовать один полный рабочий поток:

**ТТК → Конструктор меню → Расчёт продуктов → Задачи → Обратный тайминг → Лист смены**

Пользователь должен иметь возможность:

1. выбрать блюдо из ТТК;
2. указать количество порций;
3. указать время выдачи;
4. получить автоматически рассчитанную потребность в продуктах;
5. получить задачи сотрудников;
6. получить время начала операций;
7. получить итоговый лист смены.

## Модель Excel

Предусмотреть отдельные листы:

### `ТТК`

Для каждого блюда:

* название;
* категория;
* подгруппа;
* цех / ответственный;
* время подготовки;
* время полной готовности;
* ингредиенты;
* единица измерения;
* норма ингредиента на одну порцию.

### `Продукты`

* название продукта;
* единица измерения;
* категория;
* остаток;
* минимальный запас.

### `Конструктор меню`

Здесь шеф формирует меню:

* дата;
* приём пищи;
* блюдо;
* количество порций;
* время выдачи.

### `Задачи`

Хранить типовые операции:

* операция;
* блюдо или заготовка;
* ответственный;
* длительность;
* необходимое время готовности;
* дополнительные параметры, если они понадобятся.

### `Списания`

Предусмотреть структуру для:

* даты;
* продукта;
* количества / веса;
* причины;
* исполнителя;
* подтверждения шефа.

### `Инвентаризация`

Предусмотреть структуру для контроля фактических остатков и расхождений.

## Расчёт продуктов

При добавлении блюда в меню:

1. взять нормы из ТТК;
2. умножить норму на количество порций;
3. объединить одинаковые продукты;
4. показать итоговую потребность.

Например, если картофель используется одновременно в нескольких блюдах, итоговый лист продуктов должен показывать суммарное количество картофеля одной строкой.

Продукты также должны иметь возможность группировки по назначению / обработке, например:

* овощи — подготовка;
* мясо — повар;
* бакалея — проверка остатков.

## Расчёт задач

Из выбранного меню система должна создавать рабочие задачи.

Например:

* разнорабочему — подготовка овощей;
* повару — приготовление;
* шеф-повару — финальная выборочная проверка.

Распределение не должно быть жёстко зашито в один экран. Оно должно опираться на данные ТТК и типовых задач.

## Обратный тайминг

Для каждого блюда известны:

* время выдачи;
* время подготовки;
* время полной готовности;
* необходимые операции.

Система должна рассчитывать, когда каждая операция должна начаться.

Пример из предметной области:

Для обеда с выдачей в 12:00:

* подготовка овощей начинается примерно в 08:00;
* основные блюда готовятся примерно в 09:30–10:30;
* финальная дегустация / контроль — около 11:40.

Эти значения являются примером бизнес-сценария, а не константами, которые нужно зашить в код.

## Лист смены

Итогом работы должен быть понятный ежедневный лист смены, содержащий:

* меню;
* количество порций;
* продуктовую матрицу;
* задачи сотрудников;
* время выполнения;
* контрольные точки.

В дальнейшем этот лист должен быть пригоден для печати или отправки в Telegram.

## Важное архитектурное требование

Не смешивать данные и расчёты с конкретным представлением Excel.

Логика должна быть организована так, чтобы её можно было тестировать отдельно:

```text
ТТК
 ↓
Меню
 ↓
calculateIngredients()
 ↓
generateTasks()
 ↓
calculateBackwardTiming()
 ↓
buildShiftSheet()
```

Но при этом **не создавать отдельную серверную БД только ради этой архитектуры**.

Excel остаётся источником и представлением данных первой версии.

Если для автоматизации потребуется код, использовать максимально простой механизм, совместимый с выбранным Excel-окружением. Не добавлять PostgreSQL, Redis, микросервисы и другую инфраструктуру без явной необходимости.

## Принцип MVP

Не пытайся сразу реализовать весь будущий продукт.

Сначала должен работать один вертикальный сценарий:

> выбрать ТТК → создать меню → указать порции → указать время выдачи → получить продукты → получить задачи → получить тайминг → получить лист смены.

После того как этот сценарий работает, можно добавлять:

* списания;
* инвентаризацию;
* остатки;
* чек-листы;
* маркировку заготовок;
* Telegram;
* дополнительные правила управления.

## Что НЕ нужно сейчас придумывать

Не выдумывай отсутствующие бизнес-правила.

Не добавляй без необходимости:

* PostgreSQL;
* отдельный backend;
* микросервисы;
* сложную авторизацию;
* сложную систему permissions;
* Telegram API;
* полноценную складскую систему;
* закупочную систему.

Подробные спецификации и дополнительный контекст будут добавляться постепенно.

Если какого-либо требования пока нет, не надо самостоятельно придумывать сложное решение. Сделай простую расширяемую реализацию и явно обозначь предположение.

## Первый этап разработки

Перед тем как создавать много кода:

1. Проанализируй требования выше.
2. Определи структуру Excel-файла.
3. Определи связи между листами.
4. Определи минимальные поля каждой сущности.
5. Определи алгоритм расчёта продуктов.
6. Определи алгоритм генерации задач.
7. Определи алгоритм обратного тайминга.
8. После этого реализуй один полный сценарий.

Используй пример из предметной области с 50 порциями для проверки логики.

Главный критерий готовности MVP:

**Шеф выбирает блюда, количество порций и время выдачи, после чего Excel автоматически превращает это в понятный план работы кухни на смену.**
