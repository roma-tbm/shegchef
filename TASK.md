# Надёжность ShegChef и согласованность CLI / Streamlit

Дата постановки: 2026-10-12. Приоритет: P1.
Статус: ПРИНЯТО Codex 2026-10-12 после независимой повторной QA Hermes.
Удалённый CI и проверка реальной смены с шефом остаются последующими этапами.
Исходная ревизия: `277db1713a0062df11cdc4b1394a0563150070e5`.
Постоянные правила: `AGENTS.md`. Источник задачи: текущий запрос пользователя.

## Роли и порядок работы

- **Codex — продакт и приёмка.** Определяет цель, границы и acceptance criteria,
  разрешает продуктовые противоречия, готовит передачу QA и принимает результат
  после независимой проверки. Не выбирает техническую реализацию без продуктовой
  необходимости и не подменяет разработчика или QA.
- **OpenCode — разработчик.** Проверяет актуальное состояние, выбирает техническое
  решение в согласованном scope, реализует его, добавляет тесты, выполняет свои
  проверки, обновляет README и `IMPLEMENTATION_REPORT.md`. Не меняет acceptance
  criteria самостоятельно и не выдаёт свои проверки за независимую QA.
- **Hermes — независимый QA.** Проверяет каждый критерий по исходникам и поведению,
  выполняет воспроизводимые проверки, фиксирует дефекты и вердикт в `QA_REPORT.md`.
  Не исправляет реализацию вместо разработчика.

Порядок: постановка Codex → реализация OpenCode → проверка Hermes → исправления
OpenCode при дефектах → повторная QA → приёмка Codex. Пользователь самостоятельно
запускает OpenCode и Hermes. Это задание не разрешает запускать других агентов.

Неясности, влияющие на пользовательское поведение или критерии, разработчик
возвращает Codex. Допущения записывает явно; независимую часть работы продолжает.
Обычные технические решения принимает самостоятельно.

## Цель

Повысить надёжность локального планировщика кухни, восстановить воспроизводимые
проверки и обеспечить одинаковые результаты CLI и Streamlit при одинаковых
входных данных. Сохранённые меню, настройки и отметки не должны теряться при
смене даты, пересчёте или экспорте.

## Scope: этапы разработчика

а также запуск Streamlit. Для интерфейсных сценариев использовать AppTest,
для чистой логики — обычные тесты. Разделить подтверждённые дефекты и гипотезы.

### D2. Восстановить воспроизводимые проверки

Найти прежние тесты в истории Git и сопоставить с локальным набором, включая
историю `26ec0ef` и родителя текущего HEAD. Восстановить полезные проверки,
сохранить локальные расширения, адаптировать проверки к согласованному поведению.
Не ослаблять ожидания ради зелёного прогона.

Убрать исключение `/tests/`, объявить необходимые тестовые зависимости и добавить

Тесты изолировать от реальных пользовательских данных.

### D3. Объединить работу с данными

Обеспечить единое определение путей и загрузку меню, настроек, статусов,
комментариев и отклонений для CLI и веба. Субботний отчёт должен поступать
в экспорт из того же выбранного набора данных. Конкретные модули, API,
способ конфигурации и формат технического решения выбирает OpenCode.

Продуктовый контракт:

- Общий каталог по умолчанию — `~/.shegchef`; пользователь может явно выбрать
  альтернативный каталог и отдельные входные файлы в обоих сценариях.
- Смена выходного пути книги сама по себе не меняет настройки, статусы,
  комментарии или отклонения выбранного набора данных.
- Сохранённая запись меню даты, включая пустую, имеет приоритет над автоматической
  заготовкой. При отсутствии записи общая политика — будняя заготовка недельного
  плана, пустое меню в выходной. Эта задача явно разрешает соответствующее
  изменение стандартного CLI-сценария; README должен объяснить переход.
- Подготовка следующего дня использует сохранённое меню целевой даты. Отсутствие
  записи и сохранённое пустое меню различаются и не подменяются демо-данными.
- Существующие сценарии демо, `--menu`, `--week`, `--fresh`, `--search`,
  масштабирования и чтения вручную изменённой книги остаются доступными.
  Для выбора книги как источника допустим явный режим; потеря этого сценария
  недопустима. Приоритет явных источников описывается и проверяется; несовместимые
  комбинации не выбираются молча. Различие выбранных источников меню не является
  доказательством расхождения расчётов при одинаковых входных данных.
- `menu.json` и `меню.json` поддерживаются без потери данных. Непересекающиеся
  даты и совпадающие записи доступны совместно. Разные записи одной даты,
  включая конфликт пустой и непустой записи, дают понятную ошибку до записи.
  Явный выбор конкретного файла позволяет разрешить выбор источника.
- Старые файлы рядом с книгой доступны через явные пути. Автоматическая миграция
  или перезапись реальных файлов не требуется. README описывает безопасный переход.
- Повреждённое хранилище не считается разрешением перезаписать его пустыми данными.
  Ошибочный ввод не повреждает ранее сохранённые записи.

Добавить регрессии найденных расхождений. Исправлять дефекты в пределах критериев
приёмки, сохраняя разделение домена, Excel и Streamlit.

Обновить README по реализованному поведению: запуск, источники и приоритет меню,

Убрать исключения AGENTS.md, TASK.md, QA_TASK.md, IMPLEMENTATION_REPORT.md и

Подготовить короткий сценарий приёмки для шефа: выбранная дата, меню и порции,

Явно перечислить неподтверждённые нормы и ограничения. Саму проверку с шефом

## Non-goals

Новые реальные рецептуры, выдуманная зависимость времени от порций, складской
учёт, сеть/БД/авторизация, отправка сообщений, переделка архитектуры, изменения
`startconcept/`. Демонстрационные нормы и фиксированные времена не превращать
в подтверждённые производственные данные. Новую зависимость обосновать в отчёте.

Не делать commit, push, merge или публикацию. Удалённый запуск Actions без push
не входит в текущую работу: подготовить конфигурацию и выполнить локальные
проверки, явно указать, что реальный CI-прогон ожидает отдельного этапа.

## Acceptance criteria

- **AC01 — воспроизводимость.** Тесты и необходимые инструкции больше не
  исключены из Git; установка тестовых зависимостей документирована. Полный
  набор запускается одной командой и проходит локально. GitHub Actions настроен
  на ту же регрессию, включая Python 3.10 и современную поддерживаемую версию.
- **AC02 — содержательные проверки.** Проверены численные потребности/единицы/
  дефицит, доступность сотрудников и перерывы, будни/пятница/суббота/воскресенье,
  пустое меню, округление масштабирования, сохранение и экспорт. Для найденных
  дефектов имеются воспроизводящие регрессии.
- **AC03 — единый результат.** Одинаковые дата, меню, настройки и отметки дают
  одинаковый план через фактический CLI и путь расчёта веба: работы, исполнители,
  начало/конец, статусы, комментарии, отклонения и причины нарушений совпадают.
- **AC04 — согласованные выходы.** Экран, Excel и текстовые маршруты согласованы
  по работам, исполнителям, времени, статусам и причинам нарушений. Проверяются
  значения и структура Excel, а не только создание файла. DONE не скрывает
  расчётное нарушение; исторические записи доступны.
- **AC05 — смена даты и пересчёт.** Переключение даты сбрасывает старый расчёт,
  экспорт и предпросмотр масштаба. Пересчёт сохраняет комментарии, отклонения и
  исторические отметки; смена блюда/порций не переносит DONE на другую работу
  из-за совпадения порядкового ID.
- **AC06 — сохранность данных.** Ошибочные настройки, повреждённые хранилища и
  конфликт двух имён меню дают понятную ошибку без изменения исходных файлов.
  Нет молчаливой потери других дат/записей. Сохранённое пустое меню отличается
  от отсутствия записи и не подменяется шаблоном.
- **AC07 — пути и совместимость.** Общий default и явные альтернативные пути
  работают для CLI и веба. Выходной путь не определяет настройки/статусы/отклонения.
  Старые файлы и Excel-сценарии доступны; приоритет источников и переход
  документированы и подтверждены проверками.
- **AC08 — реальная смена.** Сценарий приёмки шефом подготовлен; нормы, остатки
  и фиксированные длительности явно обозначены как неподтверждённые там, где
  нет источника. Проверка реальной смены обозначена следующим ручным этапом.

## Результат OpenCode и передача Hermes

OpenCode заполняет `IMPLEMENTATION_REPORT.md`: фактический diff, происхождение
восстановленных тестов, подтверждённые/опровергнутые проблемы, команды и результаты,
соответствие AC01–AC08, ограничения и вопросы. Указывает точный HEAD и состояние
незакоммиченных изменений, включая новые файлы, чтобы QA проверял именно этот результат.

OpenCode не редактирует TASK.md, AGENTS.md, QA_TASK.md и QA_REPORT.md. Исправление
`.gitignore` для этих файлов разрешено. README обновляется разработчиком после
реализации. Старый QA_REPORT.md относится к прежней задаче и не доказывает
качество текущего результата.

После отчёта разработчика Codex готовит QA_TASK.md с точным состоянием изменений,
командами воспроизведения и ожидаемыми результатами. Hermes независимо проверяет
AC01–AC08 и ведёт новый QA_REPORT.md. При невозможности проверки критерий отмечается
непроверенным с причиной, а не пройденным. После исправлений повторяется QA.
Финальная приёмка — решение Codex по критериям и независимым доказательствам;
зелёные тесты OpenCode сами по себе её не заменяют.

## Возврат разработчику после первого отчёта — 2026-10-12

Codex сверил отчёт с исходниками рабочего дерева. Это продуктовое ревью,
не независимая QA; заявленные 589 passed пока не перепроверены Hermes.
Полезные изменения D1–D4 сохранить. Следующие замечания относятся к уже
согласованным AC03, AC05, AC06, AC07, а не к новому scope.

### R1. Общий набор данных должен использоваться фактическим веб-сценарием

В app.py bootstrap по-прежнему берёт menu_store.default_store_path, а загрузка
меню — load_days одного файла. Новый Dataset там не используется. Поэтому
SHEGCHEF_DATA_DIR влияет на CLI, но не на обычный запуск веба; второе имя меню
и конфликты веб также не проверяет.

Требуемое поведение: CLI и обычный запуск Streamlit используют один выбранный
набор данных, одинаково читают оба имени меню и показывают конфликт до записи.
Явный выбор отдельного файла позволяет разрешить конфликт в обоих сценариях.
Настройки/статусы/отклонения/отчёт берутся из выбранных путей. Не требуется
специальный UI для путей: документированная конфигурация запуска достаточна,
если её использует фактическое приложение. Подмена session_state в тесте
не является доступным пользователю способом конфигурации запуска.

Проверка: запуск AppTest с альтернативным каталогом без ручной подмены store;
меню только в меню.json; непересекающиеся даты двух файлов; конфликт одной
даты; явный выбор файла; сохранение без потери исходных данных.

### R2. Отсутствующее меню следующего дня не подставлять из выходной книги

build._next_day_menu при отсутствии записи вызывает _book_plan_menu;
app.next_day_menu_for использует только сохранённые записи. Воскресная
подготовка по одним данным по-прежнему может разойтись в CLI и вебе.

Требуемое поведение: без сохранённого меню целевой даты оба интерфейса
показывают его отсутствие, даже если в выходной книге есть недельная заготовка.
Пустая сохранённая запись остаётся пустой. Явный Excel-сценарий остаётся
доступным как отдельно выбранный источник, а не неявная подстановка.
Регрессия test_cli_data_store, ожидающая план книги при отсутствии записи,
должна проверять согласованный контракт D3, а не закреплять расхождение.

### R3. Защита распространяется на все согласованные хранилища

В отчёте повреждённые settings/notes/statuses/reports отнесены к будущей задаче.
Это противоречит AC06: их загрузчики всё ещё возвращают пустые данные при
ошибке, а последующее сохранение может заменить повреждённое содержимое.

Требуемое поведение: повреждённые файлы дают понятную ошибку при чтении и
сохранении; исходные байты не изменяются. Проверить также корректный JSON
неверной структуры, а не только синтаксически битый текст. Отсутствие файла
остаётся допустимым отдельным состоянием. Ошибочные пользовательские настройки
не меняют существующие данные. Покрыть меню, настройки, заметки/отклонения,
статусы и отчёты через используемые интерфейсами операции.

### R4. Выходная книга не должна молча выбирать меню старой даты

build._from_menu читает непустые строки существующего --out до сохранённого
меню и --menu-file. При смене даты старое меню книги переносится на новый
день; явный выбранный JSON может игнорироваться. Это нарушает стандартный
сценарий D3 и согласованность данных при переключении даты.

Требуемое поведение: без явного выбора Excel-источника меню текущей даты
берётся по общей политике D3; наличие выходной книги не меняет этот выбор.
Сохранённая пустая дата не заменяется строками книги. При отсутствии записи
используется общая будняя/выходная политика. Существующий сценарий правки
Excel сохранить через явный выбор источника и документировать переход.
Регрессии: одна выходная книга для двух дат с разным меню; сохранённая пустая
дата при непустой книге; явно выбранный JSON при существующей книге;
явный Excel-сценарий с ручной правкой остаётся работоспособным.

### R5. Сквозная проверка должна проходить через оба интерфейса

test_cli_and_web_style_calculation_agree собирает веб-сценарий вручную через
build_scenario с уже выбранными данными. Он проверяет ядро, но пропускает
bootstrap, выбор путей и загрузку app.py, где сохранились расхождения R1.

### R6. JSON null не является отсутствующим файлом (AC06 / R3)

Codex выполнил ограниченное воспроизведение на временных файлах: Dataset.load_menu_days
для menu.json с текстом null возвращает {}, тогда как прямой menu_store.load_days
поднимает MenuStoreError. Для null в settings/notes/statuses/reports штатные
загрузчики поднимают соответствующие StoreError. Уточнение к отчёту Hermes:
Dataset._load_one загружает только меню, не все пять типов хранилищ.

Требуемый результат: существующий файл с null или другим скалярным JSON —
понятная ошибка, а не отсутствие записи, во всех доступных путях загрузки;
истинное отсутствие файла остаётся допустимым. Добавить регрессии null,
false, числа и строки через Dataset и используемые CLI/вебом загрузчики.
Проверить отказ от сохранения поверх неверного файла и сохранность байтов.
Для остальных четырёх хранилищ не требовать несуществующего Dataset API:
проверять их штатные загрузчики и соответствующие сценарии интерфейсов.

### R7. Сохранение должно соответствовать выбранному источнику (AC05–AC07 / R1)

PASS дополнительного сценария в переданном отчёте Hermes не доказывает
требуемое поведение: неизменность меню.json при записи menu.json — не проверка
сохранения в явно выбранный отдельный файл. В текущем app.persist_store
сохранение всегда идёт в dataset().menu, тогда как чтение может идти
из SHEGCHEF_MENU_FILE или menu_alt. Реализовать и проверить полный round-trip.

Обязательные сценарии:

1. Задать SHEGCHEF_MENU_FILE на отдельный JSON вне выбранного каталога данных,
   изменить порции через веб, переключить дату и открыть новую сессию.
   Правки сохраняются в выбранном файле и загружаются обратно; посторонний
   menu.json не создаётся/не меняется без явного выбора.
2. Оставить запись выбранной даты только в меню.json и другие даты в menu.json.
   Изменить порции этой даты через веб и переоткрыть приложение. Правка
   сохранена, не создан конфликт одной даты между файлами, другие даты целы.
3. Повторить при конфликте: без явного выбора записи запрещены, с явным
   выбором сохраняется выбранный источник, второй файл остаётся неизменным.
